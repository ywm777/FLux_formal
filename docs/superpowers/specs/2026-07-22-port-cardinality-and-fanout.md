# 端口基数与多下游连接架构

日期：2026-07-22

## 1. 问题

旧模型把所有端口缺省容量统一设为 `one`。这使输出端口在已有一条边后被画布判定为占用，虽然执行引擎本身能够把同一输出广播给多条出边，用户却无法在编辑器中建立这种流程。

同时，旧连接手势把“从已连接端口拖动”隐式解释为重连。对于可分支输出，这会把“新增下游”和“调整旧边”混成同一个动作。

## 2. 架构决策

### 2.1 方向决定缺省容量

- 输入端口默认 `one`：一个输入只接受一个上游。
- 输出端口默认 `many`：一个结果可以广播给多个下游。
- 节点作者可把输出显式声明为 `one`，表达一次只能进入一个后续路径的业务约束。
- 暂不允许自定义节点把输入声明为 `many`。在开放前必须先定义聚合顺序、失败传播和重复键冲突语义。

缺省规则由 Node SDK 的领域函数统一提供，Schema、画布桥接、节点工作室和连接策略不得分别推断。

### 2.2 新建分支与重连分离

连接手势遵循下列状态转换：

```text
拖动端口
  ├─ 选中的既有边经过该端口 -> reconnect
  ├─ 端口仍有容量             -> create
  └─ 容量已满                 -> blocked
```

因此，从已使用的 `many` 输出拖动总是创建新分支。只有用户先选中一条具体边，再从该边端口拖动时，才进入重连。该规则消除了隐式猜测，也避免多条出边时无法判断要移动哪一条。

### 2.3 持久化迁移

工作流 Schema 从 V1 升级到 V2：

- V1 输入端口迁移为 `one`。
- V1 输出端口迁移为 `many`。
- V2 以后按工作流中显式保存的 `capacity` 解析。

V1 产品没有让用户主动选择“单下游输出”的入口，因此历史输出上的 `one` 都来自旧的错误缺省值，可以安全迁移为 `many`。迁移保持源对象不可变。

## 3. 模块职责

| 模块 | 职责 |
| --- | --- |
| `@flux/node-sdk/port-capacity` | 定义方向缺省值与容量解析，是唯一领域规则来源 |
| `@flux/workflow-schema` | 保存显式容量并迁移旧工作流 |
| `canvas/connection/cardinality` | 纯函数判断 create、reconnect 或 blocked |
| `canvas/connection/policy` | 把画布节点、端口和边适配到纯容量规则，并执行类型、重复边、环路校验 |
| `useCanvasConnectionController` | 只负责手势生命周期和反馈，不自行猜测连接语义 |
| Node Studio | 允许节点作者选择输出容量；输入保持单上游 |
| Workflow Runtime | 将同一源端口产出的值投递给每条已激活的出边 |

## 4. 不变量

1. 一个 `many` 输出可以连接任意多个不同下游输入。
2. 同一对逻辑端口之间不能创建重复边。
3. 一个 `one` 输入不能同时连接两个上游。
4. 一个显式 `one` 输出不能同时连接两个下游。
5. 选中某条边是进入重连模式的必要条件。
6. 多下游不能绕过类型检查、环路检查或原子化边命令。

## 5. 验证策略

- Node SDK 与 Workflow Schema：缺省值、V1→V2 迁移及不可变性单测。
- Canvas 领域层：容量与连接起始意图纯函数单测。
- Canvas 集成契约：连接策略、手势控制器和持久化桥接共享同一规则。
- 产品回归：旧工作流加载后，在同一输出上创建至少两个下游，并确认执行结果沿每条出边传播。
