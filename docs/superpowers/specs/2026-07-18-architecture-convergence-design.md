# Flux 整体架构收敛设计

- 日期：2026-07-18
- 状态：实施中（桌面应用边界与 Schema 迁移已落地）
- 策略：全仓检查、桌面端优先、分阶段迁移

## 1. 目标

在不改变 Flux 当前产品形态和核心操作习惯的前提下，对桌面端、云端 API、共享包、本地存储、数据格式和测试体系做一次完整架构检查，并按风险与收益分阶段重构。

本次整理优先保证现有功能稳定、降低回归风险，同时让后续功能不再持续堆入巨型组件、全局 Store 和通用 `lib` 目录。

## 2. 已确认约束

1. 保留当前工作台、画布、账户、分享和 AI 接入等产品形态。
2. 允许统一导航、状态表达和产品术语，但不进行视觉大改版。
3. 检查范围覆盖整个仓库，实施顺序以桌面端为主。
4. 架构整理期间冻结核心新功能，只接受缺陷修复和必要调整。
5. 现有本地数据、云端数据和工作流文件允许执行一次自动迁移。
6. 自动迁移必须可验证、可重试、失败可回退，不能静默丢失用户数据。
7. 采用目标架构收敛与分阶段迁移，不进行新旧系统并行重写。
8. 每一阶段结束时应用都必须可以构建、启动和完成核心流程验证。

## 3. 当前架构判断

### 3.1 可保留的基础

- Monorepo 已经形成 `apps/desktop`、`apps/api` 和多个 `packages/*` 的基础边界。
- `workflow-schema`、`workflow-runtime`、`node-sdk`、`canvas-core`、`shared` 和 `ui` 已具备领域拆分雏形。
- API 已按认证、工作流、执行、AI、应用、节点和市场等模块组织。
- 本地与云端工作空间已有 Repository 抽象的初步实现。
- 现有合同测试和端到端测试可作为行为基线的一部分。

### 3.2 需要治理的热点

- `CanvasView`、`TitleBar`、`WorkbenchView`、`FluxNode` 和 `AiConnectionDrawer` 承担过多职责。
- 页面组件同时处理展示、数据加载、持久化、执行、冲突处理和快捷键。
- Zustand 中的多个 `*Nonce` 字段承担跨组件事件总线职责，调用路径难以追踪。
- `apps/desktop/src/lib` 同时容纳领域转换、基础设施、产品错误、文件处理和执行逻辑，归属不清。
- 本地与云端差异会向页面和 Store 泄漏，增加分支和状态组合。
- 当前仓库只有初始化提交，大量成果仍在工作区中；实施前必须建立非破坏性的可回退基线。

## 4. 目标产品域

产品与代码边界统一围绕五个业务域：

1. **工作空间与身份**：本地/云端空间、登录、账户与启动恢复。
2. **工作流创作**：工作台、画布、节点、连线、模板和导入导出。
3. **工作流执行**：校验、试运行、正式执行、取消、进度与结果。
4. **分享与集成**：发布、分享、AI 连接、外部应用与节点市场。
5. **应用外壳**：导航、顶栏、窗口、快捷键和全局反馈。

核心用户路径保持不变：

```text
进入工作空间 → 在工作台选择工作流 → 在画布编辑
→ 保存或执行 → 查看状态与结果 → 按需发布或分享
```

## 5. 总体技术分层

### 5.1 分层

1. **表现层**：React 页面、组件、Tauri 窗口和用户输入。
2. **应用层**：打开、保存、执行、发布、分享和切换空间等完整用例。
3. **领域层**：工作流 Schema、运行规则、节点契约和纯画布逻辑。
4. **端口与适配器层**：本地文件、云端 API、数据库、队列、凭证和 AI Provider。

依赖方向固定为：

```text
表现层 → 应用层 → 领域层
             ↓
           能力端口 ← 本地/云端/数据库等适配器
```

### 5.2 依赖规则

- 页面不能直接调用文件系统、数据库或具体 API 端点。
- 应用用例通过端口访问外部能力，不判断本地或云端实现细节。
- 领域包不能依赖 React、Tauri、NestJS、数据库或网络客户端。
- `packages/*` 可以被 `apps/*` 引用，但不能反向引用应用代码。
- 跨层输入输出使用明确类型，不传递框架对象或隐式全局状态。
- 不为追求目录整齐而提前创建大量新包；先校准现有包职责。

## 6. 桌面端目标结构

```text
apps/desktop/src/
├─ app/                    启动、应用外壳、导航和组合根
├─ features/
│  ├─ workspace/          本地/云端空间与启动恢复
│  ├─ workbench/          列表、搜索、模板和导入导出
│  ├─ canvas/             编辑、选择、历史、节点和连线
│  ├─ execution/          执行、取消、进度和结果
│  ├─ sharing/            发布与分享
│  ├─ auth/               登录与账户
│  └─ ai-connections/     AI 服务连接
├─ infrastructure/
│  ├─ local/              Tauri、文件和本地存储适配器
│  └─ cloud/              API 客户端与云端适配器
└─ shared/                仅限桌面端通用且无业务归属的代码
```

### 6.1 组件职责

- `CanvasView` 收敛为画布界面的组合组件。
- 工作流加载与保存进入 `CanvasSession` 或等价的会话控制器。
- 历史、选择、连线策略、快捷键和执行分别由独立控制器或 Hook 管理。
- `TitleBar` 拆为导航、工作流操作、空间切换、账户菜单和窗口控制。
- `WorkbenchView` 不再直接负责 Repository 调用、文件导入导出和删除流程。
- ReactFlow 类型只能停留在画布表现与适配层，不能进入持久化和领域接口。

### 6.2 状态与命令

Zustand 继续用于需要跨组件观察的会话状态，例如当前工作流、保存状态、运行进度、选中对象和面板开关。

跨组件动作改成明确命令，不再使用 `saveNonce`、`publishNonce`、`testRunNonce` 等递增信号：

```text
用户点击保存
→ WorkflowCommands.save()
→ CanvasSession 生成领域快照
→ WorkspaceRepository.save(snapshot)
→ Session 更新保存结果
→ 顶栏和状态栏根据同一状态自动刷新
```

## 7. 共享包职责

### `@flux/shared`

只保留跨应用稳定共享的标识、DTO、状态枚举、错误代码和小型无副作用工具，不承载具体业务流程。

### `@flux/workflow-schema`

作为工作流持久化与交换格式的唯一来源，负责 Schema、版本号、解析、校验和迁移入口。

### `@flux/workflow-runtime`

负责可重复测试的执行编排，不直接访问网络、文件、数据库或用户凭证；外部能力通过执行端口注入。

### `@flux/node-sdk`

负责节点定义、端口、配置、运行契约、注册表和内置节点，不负责桌面渲染与云端持久化。

### `@flux/canvas-core`

保留框架无关的图操作、序列化、视口和可复用编辑规则，不暴露 ReactFlow 组件或浏览器对象。

### `@flux/ui`

只包含设计令牌和可复用表现组件；业务文案、数据加载和应用命令留在对应 Feature。

## 8. API 目标结构

每个 NestJS 模块统一为以下职责：

```text
Controller / Transport
        ↓
Application Use Case
        ↓
Domain / Shared Runtime
        ↓
Repository、Queue、Credential、Provider Ports
        ↑
Database、Redis、Memory、File、AI Adapters
```

- Controller 只处理协议、认证上下文、DTO 转换和响应码。
- Service 不再同时承担用例、存储、执行调度和展示格式转换。
- 内存、文件和 TypeORM Repository 必须通过同一组合同测试。
- 执行队列、取消注册表和执行处理器通过明确接口协作。
- AI 凭证只能在基础设施边界解密和使用，不能进入共享领域对象或日志。
- 保留现有 API 行为；需要调整的接口先增加兼容适配，再迁移调用方。

## 9. 数据版本与自动迁移

### 9.1 工作流文档

- 所有持久化工作流增加或规范化 `schemaVersion`。
- 迁移以连续注册表实现，例如 `v1 → v2 → v3`，不允许跨版本散落条件判断。
- 读取旧数据时先保留原始内容，再迁移并校验目标 Schema。
- 只有在迁移和写入都成功后才原子替换原数据。
- 失败时保留原文件，进入只读恢复或导出流程，并向用户给出可操作提示。
- 导入的 `.flux` 文件使用同一迁移链，避免本地、云端和导入流程产生不同规则。

### 9.2 云端数据

- 数据库结构变更使用显式迁移，不依赖生产环境自动同步。
- API 在过渡期兼容旧 DTO，内部立即转换为当前领域模型。
- 迁移任务可重复执行，并记录版本、时间和结果。
- 任何不可逆迁移都必须先备份，并提供对应的恢复步骤。

## 10. 错误处理

- 统一错误分类：校验、冲突、认证、权限、网络、执行、迁移和未知错误。
- 应用层返回可识别错误，不把原始数据库、文件系统或 Provider 异常直接交给界面。
- 界面通过统一映射生成用户可理解、可恢复的提示。
- 日志保留技术上下文，但不得包含令牌、凭证、工作流敏感输入或用户隐私数据。
- 自动保存、执行和迁移失败不得覆盖最后一次有效数据。

## 11. 验证策略

### 11.1 重构前行为基线

- 固化本地启动、空间恢复、新建、打开、编辑、保存、执行、分享和导入导出路径。
- 保留现有合同测试，并区分真正的行为合同与依赖源码文本的脆弱检查。
- 为当前支持的数据版本准备脱敏固定样本。

### 11.2 分层测试

- 领域层：纯单元测试和属性边界测试。
- 应用层：使用内存端口测试完整用例、失败与重试。
- 适配器层：本地/云端 Repository、文件和 API 合同测试。
- 迁移层：旧版本样本、重复迁移、失败回退和数据完整性测试。
- 界面层：核心交互组件测试与少量关键端到端流程。
- 每个阶段至少执行类型检查、构建、相关测试和桌面应用启动检查。

## 12. 分阶段实施

### 阶段 0：安全基线

- 记录现有工作区状态，禁止覆盖或清理用户已有改动。
- 建立当前可通过的类型检查、构建和核心流程基线。
- 固化关键数据样本与行为合同。
- 明确每个实施批次的文件范围，避免多个重构方向同时交叉修改。

### 阶段 1：端口与应用命令

- 定义 Workspace、Execution、Auth、Storage 等端口。
- 在不改变界面的情况下，让现有实现通过端口接入。
- 建立 `WorkflowCommands` 和画布会话边界。

### 阶段 2：桌面端热点拆分

- 按加载保存、编辑、执行、快捷键和界面组合逐步拆分 `CanvasView`。
- 拆分 `TitleBar`、`WorkbenchView`、`FluxNode` 和 AI 连接界面。
- 每拆一块就运行现有测试并启动应用检查视觉与交互。

### 阶段 3：共享包与数据迁移

- 校准六个共享包的职责和依赖方向。
- 建立统一 Schema 版本和迁移注册表。
- 让本地、云端和文件导入使用相同迁移入口。

### 阶段 4：API 边界治理

- 收敛 Controller、Application Service、领域逻辑和适配器职责。
- 统一 Repository、执行队列和 AI Provider 合同测试。
- 清理仅为旧调用路径保留的兼容层。

### 阶段 5：收尾与文档

- 删除确认无调用的旧实现和重复转换。
- 增加依赖边界检查和架构决策记录。
- 更新 README、技术文档和开发约定。
- 完成全仓验证与最终桌面体验检查。

## 13. 成功标准

1. 当前产品页面、主要操作路径和视觉语言保持稳定。
2. 保存、执行、发布和分享各自只有一条可追踪的应用命令路径。
3. 页面组件不直接访问具体 Repository、文件系统或 API 实现。
4. 移除以 `*Nonce` 充当跨组件命令总线的模式。
5. 本地与云端适配器通过同一组核心合同测试。
6. 旧工作流样本能够自动迁移，失败时原始数据保持完整。
7. 领域包不依赖 React、Tauri、NestJS、数据库或网络客户端。
8. 每个实施阶段均通过约定的类型检查、构建、测试和启动验证。
9. 架构文档能够说明每个模块的职责、使用方式和依赖边界。

## 14. 明确不做

- 不重新设计已经符合预期的核心产品流程。
- 不在本轮引入微服务、事件溯源或新的状态管理框架。
- 不为了缩短单个文件而制造没有业务边界的碎片组件。
- 不同时维护一套长期存在的“新版 Flux”。
- 不借架构整理顺带开发新的核心业务功能。

## 15. 主要风险与应对

- **未提交改动范围大**：先建立非破坏性基线，所有修改按小批次记录和验证。
- **重构引入隐性行为变化**：先补行为测试，再移动职责，不同时重写逻辑。
- **本地与云端产生偏差**：通过统一端口与合同测试约束两类适配器。
- **迁移损坏用户数据**：原始数据备份、目标校验、原子写入和失败回退缺一不可。
- **目录变整齐但复杂度未下降**：验收以调用路径、依赖方向和可测试性为准，而非文件数量。

## 16. 阶段 5 实施证据（底座稳定性与转场动效）

完成日期：2026-07-20。

本阶段先处理基础设施边界和页面切换体验，未改变工作流编辑、执行和分享的用户流程。

### 已落地

- `WorkflowsController` 与 `ExecutionsController` 的请求体改为 `class-validator` DTO；未知字段由全局 `ValidationPipe` 清理，工作流图仍由 Schema 在应用服务层校验。
- 根构建脚本拆分为 `build:packages` 与 `build:apps`。完整性测试现在同时验证 packages、API 和 Desktop 构建，并执行 DTO smoke 与 Controller 边界合同。
- Workspace Repository 改为 `createWorkspaceRepository(kind)` 工厂，组合根按当前空间创建固定适配器实例；任务列表操作使用显式 scope，不再在每个请求中读取全局 Store 决定目标。
- 工作台与画布保持双层挂载，通过 `.app-view-layer` 使用 `opacity + translate3d` 进行 200ms 进入、160ms 退出的合成层过渡；活动层立即可交互，非活动层禁用指针事件，并支持 `prefers-reduced-motion`。

### 验证证据

```text

pnpm --filter @flux/desktop typecheck

```

动效采用统一的 150–300ms 交互节奏，仅动画 `opacity` 与 `transform`，不阻塞点击或键盘输入。下一批继续处理本地存储原子写入/备份与执行审批 checkpoint；大组件拆分仍按风险独立推进。
