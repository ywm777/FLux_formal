# Flux 节点业务规划与现实用途审计

> 本文只描述两类事实：仓库中已经实现并可由测试验证的能力，以及 PRD 已明确规划但仍缺基础设施的能力。未接通的能力不得用“可用”口吻描述。

## 1. 目标

Flux 的节点目录不以数量为目标，而以“能否组成真实、可重复、可观察的业务闭环”为目标。

每个公开节点必须回答七个问题：

1. 谁会用它？
2. 在什么现实事件发生后使用？
3. 输入是什么？
4. 它实际执行什么动作？
5. 输出给谁或给哪个下游步骤？
6. 一个具体业务案例是什么？
7. 它不能做什么、依赖什么基础设施？

无法回答或代码行为与名称不一致的节点，不进入公开目录。

## 2. 事实边界

- PRD 的首期目标用户是个人自动化用户、业务运营和开发者；团队管理不是近期目标。
- PRD 的 MVP 只承诺手动触发、HTTP 请求、延时、条件分支、日志输出五个基础节点。
- 当前执行引擎能够按 DAG 拓扑顺序运行，并按激活的输出端口跳过未命中的分支。
- 当前 `ctx.invoke` 仍直接报“载体调用未实现”，所以授权应用节点尚不能形成业务闭环。
- API 层虽有 Ollama 调用服务，但现有三个 AI 节点没有调用该服务：分析和生成返回占位文本，AI 决策固定走“是”。
- 定时触发节点只在被执行时返回时间戳，仓库中没有按 Cron 自动创建执行的调度器。
- 延时节点使用进程内计时器等待，不是可恢复的持久化延时任务。
- 当前公开目录只有文本输入、JSON 格式优化、JSON 展示三个节点，其余节点保留在执行注册表中供审计。

## 3. 用真实流程倒推节点

### 流程 A：人工整理 JSON（当前可运行）

**使用者**：开发者、接口测试人员、运营技术支持。

**现实任务**：用户从日志、接口文档或聊天中复制一段 JSON，希望校验格式、统一缩进、按键名排序并复制结果。

`文本输入 → JSON 格式优化 → JSON 展示`

该流程不依赖第三方凭证、调度器或 AI，是当前可以完整验证的最小闭环。

### 流程 B：拉取接口数据并按规则处理（基础节点验收流程）

**使用者**：开发者、懂 API 的运营人员。

**现实任务**：人工运行一次接口检查，读取响应，解析 JSON，确认关键字段存在，再根据状态进入成功或异常路径，最后写入运行日志。

`手动触发 → HTTP 请求 → JSON 解析 → 数据校验 → 条件分支/规则分流 → 记录结果`

单节点代码基本存在，但 HTTP 安全、超时、凭证和生产级重试仍需补齐，完成前只能作为本地测试能力。

### 流程 C：整理名单并生成可发送文本（数据处理流程）

**使用者**：内容运营、增长运营、个人效率用户。

**现实任务**：导入 CSV 或接口返回的名单，去重和排序，补充活动信息，再生成逐条通知或摘要文本。

`文本/文件输入 → CSV 转换 → 列表处理 → 合并对象 → 模板渲染 → 预览/导出`

目前缺少真实文件输入和导出节点；现有数据处理节点可以验证中间逻辑，但还不是完整交付流程。

### 流程 D：每日信息简报（目标流程，当前不可自动运行）

**使用者**：个人用户、内容运营、研究人员。

**现实任务**：每天固定时间拉取已授权或公开的信息源，解析后由模型提炼重点，再发到用户授权的应用。

`定时触发 → HTTP/授权应用读取 → JSON 解析 → AI 分析 → 人工复核（可选）→ 授权应用发送`

该流程依赖 Cron 调度器、真实 AI 调用、应用授权调用和投递结果回执；现阶段模板只能演示结构，不能宣称已实现自动简报。

### 流程 E：业务事项自动分流（目标流程，当前缺入口和交付）

**使用者**：客服运营、销售运营、表单负责人。

**现实任务**：表单或系统通过 Webhook 提交事项，先校验必要字段，再按优先级或类型分流，写入用户授权的系统并通知负责人。

`Webhook 触发 → 数据校验 → 规则分流 → 授权应用动作 → 发送结果/HTTP 响应`

当前缺少 Webhook 触发、通用授权应用动作和 HTTP 响应节点，因此只具备中间规则处理能力。

## 4. 现有 28 个节点逐项审计

状态含义：

- **公开**：当前已有可验证业务闭环。
- **候选**：实现与现实用途一致，但必须补足列出的验收项后才能公开。
- **基础设施后**：用途真实，但底层能力尚不存在或不可恢复。
- **合并**：用途存在，但不值得作为独立一级节点，应并入更通用节点。
- **重做**：当前实现会误导用户，不能继续按现状使用。

### 4.1 入口

| 节点 | 现实用途 | 输入 → 实际动作 → 输出 | 具体业务案例 | 当前边界与决策 |
| --- | --- | --- | --- | --- |
| 手动触发 `flux.trigger.manual` | 由用户明确启动一次流程，适合临时检查、批处理和调试 | 无输入 → 记录启动时间 → `startedAt` | 运营人员点击运行，检查一次活动接口并生成结果 | 当前“运行预览”本身已经能启动流程，节点主要表达流程入口；需明确发布后手动运行语义。**候选** |
| 定时触发 `flux.trigger.cron` | 按日、周或固定周期执行报表、同步和提醒 | Cron 与时区 → 被调用时回传当前时间 → 触发信息 | 每天 09:00 拉取昨日数据 | 没有调度器，保存 Cron 不会自动运行。完成持久化调度、错过执行策略和时区测试后再开放。**基础设施后** |
| 文本输入 `flux.input.text` | 让用户粘贴文本、JSON 或 CSV 作为一次处理任务的源数据 | 配置文本 → 非空校验 → `{text}` | 粘贴接口返回的 JSON 做格式校验 | 当前是配置时固定输入，不是运行时表单；适合开发工具流程。**公开** |
| 设置数据 `flux.data.setValue` | 为流程提供固定参数、规则或测试数据 | JSON/文本配置 → 尝试解析 JSON → 原值或对象 | 给日报流程配置关键词、条数和地区 | 与“文本输入/结构化输入”职责重叠，而且会忽略上游输入。应合并为“手动输入”节点的文本/JSON模式。**合并** |

### 4.2 处理

| 节点 | 现实用途 | 输入 → 实际动作 → 输出 | 具体业务案例 | 当前边界与决策 |
| --- | --- | --- | --- | --- |
| JSON 格式优化 `flux.transform.jsonFormat` | 校验 JSON，统一键名格式、字符串大小写、空值、排序与缩进 | 文本路径 → 解析、递归规则转换、冲突校验、格式化 → `{value,data}` | 将接口字段转为 camelCase、清理字符串并生成稳定 JSON | 键名转换冲突会中止执行；不负责把任意 API 响应自动映射成业务模型。**公开** |
| JSON 解析 `flux.transform.json` | 在 JSON 字符串与结构化对象之间转换，供下游按字段使用 | 路径与模式 → `JSON.parse` 或 `JSON.stringify` → 对象或字符串 | 把 HTTP 响应的 `body` 字符串解析为订单对象 | 与“格式优化”不同：这是机器处理节点，不强调展示。需补输入输出契约测试。**候选** |
| 字段提取 `flux.transform.extract` | 从嵌套响应中取出某个字段并重命名 | 对象与路径 → 路径读取 → `{自定义键: 值}` | 从 `body.items.0.orderId` 提取订单号 | 路径不存在时会输出 `undefined`，需提供缺失策略。**候选** |
| 模板渲染 `flux.transform.template` | 把结构化数据拼成消息、标题、文件名或请求体 | 对象与 `{{path}}` 模板 → 占位符替换 → `{text}` | 将客户姓名和订单号生成通知文本 | 只有简单路径替换，没有条件、循环、转义和默认值。**候选** |
| 文本处理 `flux.text.transform` | 清理空格、替换词、拆分/合并文本、转换大小写 | 文本/数组与操作 → 确定性转换 → `{value,count?}` | 清理表单字段，按换行拆分关键词 | 不是富文本、自然语言处理或编码检测。**候选** |
| 正则提取 `flux.text.regex` | 从半结构化文本中提取邮箱、订单号、日期等有固定模式的内容 | 文本与正则 → 匹配最多 100 项 → `{matches,count}` | 从客服记录中提取工单编号 | JavaScript 正则没有执行超时，复杂表达式可能阻塞；加长度和安全限制后再开放。**候选** |
| Base64 编解码 `flux.transform.base64` | 处理 API 中以 Base64 表示的小型文本字段 | 文本与编码/解码模式 → Base64 转换 → `{value,operation}` | 解码 webhook 中的 Base64 文本载荷 | Base64 不是加密；不适合大文件或密钥保护。应放入“高级工具”，不默认展示。**候选** |
| 合并对象 `flux.data.merge` | 将上游业务对象与固定元数据合并，并选择覆盖策略 | 对象、附加 JSON、策略 → 浅合并 → 合并对象 | 给表单记录补充渠道和活动 ID | 仅浅合并，不处理深层冲突。**候选** |
| 列表处理 `flux.data.list` | 对名单或接口数组去重、排序、截取、反转、扁平化 | 数组与操作 → 列表转换 → `{items,count}` | 对报名名单按用户 ID 去重并取前 100 条 | 不包含逐项映射和条件过滤；后者应由“遍历/过滤”能力承担。**候选** |
| CSV 转换 `flux.transform.csv` | 在 CSV 文本和对象列表之间转换 | CSV/数组与分隔符配置 → 解析或序列化 → 行、对象或文本 | 把活动报名 CSV 转为对象列表 | 当前是文本处理，不会读取或保存文件；需要文件节点才能形成导入导出闭环。**候选** |
| 数学运算 `flux.logic.math` | 计算金额、比例、分数、阈值或舍入值 | 两个数字/路径与运算 → 四则/取模/极值/舍入 → `{value,...}` | 计算折后价或线索评分 | 只支持两个操作数，不是公式引擎，也不处理货币精度。**候选** |
| 数据校验 `flux.logic.validate` | 在写入系统或发送通知前检查必填字段和基本类型 | 数据与规则 → 校验 → `valid` 或 `invalid` 分支及问题列表 | 缺少客户 ID 时进入异常处理，不写入 CRM | 只支持必填和五种基础类型，没有格式、范围和业务唯一性校验。**候选** |
| 日期时间 `flux.time.format` | 计算截止时间、转换时区并生成展示文本 | 时间、增量、地区与时区 → 加减和格式化 → ISO/时间戳/文本 | 把 UTC 订单时间转换为上海时间，或计算 7 天后到期日 | 按固定毫秒增加日/周，不是工作日历，也不处理节假日。**候选** |
| 构建请求地址 `flux.network.url` | 将基础 URL 与查询参数安全编码后组合 | URL、静态/输入参数 → `URLSearchParams` → `{url}` | 为分页查询拼接关键词、页码和筛选条件 | 大多数用户会在 HTTP 节点内配置查询参数；独立节点增加目录噪音。并入 HTTP 请求的“查询参数”配置。**合并** |

### 4.3 流程控制

| 节点 | 现实用途 | 输入 → 实际动作 → 输出 | 具体业务案例 | 当前边界与决策 |
| --- | --- | --- | --- | --- |
| 条件分支 `flux.logic.condition` | 根据布尔业务规则选择两条路径 | 数据与表达式 → 安全表达式求值 → `true` 或 `false` | 金额大于 1 万时进入人工复核，否则自动处理 | 只适合二选一；需在界面提供可理解的规则构建器和表达式错误提示。**候选** |
| 规则分流 `flux.logic.switch` | 根据状态、地区或类型选择多个固定路径 | 字段路径与两个匹配值 → 值比较 → `case1`、`case2` 或 `default` | 工单按 `urgent/normal` 分流 | 当前只有两个显式规则，扩展性差；应重做为可增删规则的多分支节点。**重做** |
| 延时 `flux.action.delay` | 在短时间内错开发送或等待外部系统完成 | 上游数据与毫秒数 → 进程内等待 → 原输入 | 两次 API 请求间等待 500 毫秒，避免触发限流 | 进程重启会丢失等待，不适合小时/天级业务。短节流可保留；长等待必须交给持久化队列。**基础设施后** |

## 5. 必须补齐、且有现实用途的新节点

以下不是为了增加数量，而是为了让上面的真实流程闭环。

| 计划节点 | 现实用途 | 输入 → 动作 → 输出 | 依赖与边界 |
| --- | --- | --- | --- |
| Webhook 触发 | 接收表单、内部系统或用户应用的实时事件 | HTTP 请求 → 验签、解析、创建执行 → 请求数据与事件元数据 | 需要公开端点、鉴权/签名、幂等键、速率限制和重放防护 |
| 文件输入 | 让用户选择本地 JSON/CSV/TXT 文件作为源数据 | 用户选定文件 → 受控读取 → 文件元数据与文本/二进制引用 | 需要 Tauri 最小文件权限、大小限制和编码检测；不能默认读取任意目录 |
| 遍历列表 | 对数组中的每一项执行同一段子流程 | 数组与并发策略 → 逐项调度子图 → 每项结果与汇总 | 需要执行引擎支持子图、并发、失败策略和顺序保证 |
| 通用授权应用动作 | 调用用户已经授权的任意应用操作，不预置固定应用白名单 | binding、action、payload → `ctx.invoke` → 应用回执 | 需要凭证加密、权限范围、撤销、审计和真实 invoke 实现 |
| HTTP 响应 | 对 Webhook 调用方返回状态码、Header 和 Body | 业务结果 → 构造响应 → 结束请求 | 只适用于 Webhook 启动的同步流程；需规定最大等待时间 |
| 导出文件 | 把 JSON、CSV 或文本结果保存为用户明确选择的文件 | 文本/二进制与文件名 → 用户确认路径后写入 → 文件信息 | 需要保存对话框、覆盖确认和受控文件权限 |
| 人工复核 | 在 AI 或高影响动作前暂停，等待用户确认、修改或拒绝 | 待审内容与截止时间 → 创建待办并持久化暂停 → 通过/拒绝/修改结果 | 需要可恢复暂停、通知和权限；没有它时 AI 结果只能作为建议，不能自动做高影响决策 |

## 6. 公开路线图

### 现有模板处置

| 模板 | 事实判断 | 处置 |
| --- | --- | --- |
| JSON 文本格式优化 | 三个节点均真实执行，结果可在节点详情中预览和复制 | 保留为公开模板 |
| 优先级自动分流 | 条件分支可以真实运行，但输入是模板内固定数据，结果只写运行日志，并未接入真实表单或业务系统 | 仅保留为内部规则演示；Webhook 和授权应用动作完成后再改造成业务模板 |
| AI 内容起草 | AI 生成节点只返回占位文本，不会调用模型 | 立即从公开模板入口隐藏 |
| 每日信息简报 | Cron 不会自动调度，AI 分析是占位实现，“保存简报”实际只是写运行日志 | 立即从公开模板入口隐藏 |

### 阶段 0：保持当前真实闭环

公开：文本输入、JSON 格式优化、JSON 展示。

### 阶段 1：完成基础 API 规则流程

按顺序审核并公开：手动触发、HTTP 请求、JSON 解析、字段提取、数据校验、条件分支、写入运行日志。

验收流程必须真实跑通：

`手动触发 → HTTP 请求 → JSON 解析 → 数据校验 → 条件分支 → 写入运行日志`

### 阶段 2：完成运营数据整理流程

补文件输入与导出后，审核 CSV 转换、列表处理、合并对象、模板渲染、文本处理、数学运算、日期时间。

### 阶段 3：完成事件与应用联动

先实现 Webhook、通用授权应用动作和 `ctx.invoke`，再开放实时事件处理与跨应用流程。

### 阶段 4：完成可恢复调度与批处理

先实现持久化 Cron、可恢复等待和遍历子图，再开放定时触发、延时和批处理能力。

### 阶段 5：完成真实 AI 闭环

AI 节点必须调用真实 AI Proxy，并具备结构化输出、用量、超时、错误、模型可用性和人工复核；占位实现全部删除后才可公开。

## 7. 分类结论

一级分类仍采用五类：入口、处理、流程、连接、输出。AI 是载体筛选，不是一级分类：AI 分析/生成属于处理，AI 决策属于流程。JSON、文本、CSV、时间、网络是搜索标签，不再各自制造一级分类。
