# Flux 节点分类方案

> 逐节点现实用途、实现边界与公开路线图见 [`node-business-plan.md`](./node-business-plan.md)。

## 当前决策

- 能力目录暂时只开放「文本输入」「JSON 格式优化」「JSON 展示」三个已验证节点。
- 历史/实验节点继续保留在执行时注册表中，但不出现在新建节点入口，避免已有工作流损坏。
- 在分类规则确认前，不再向用户目录追加节点。

## 分类模型

节点使用三个互相独立的维度，避免把“它在流程中的作用”和“它由什么能力执行”混为一谈。

### 1. 主分类：节点在工作流中的作用

主分类只保留五类，并保持互斥：

| ID | 用户名称 | 边界 | 典型节点 |
| --- | --- | --- | --- |
| `source` | 入口 | 创建一次执行或产生初始数据 | 手动触发、定时触发、文本输入、设置数据 |
| `transform` | 处理 | 对输入做确定性或智能处理，主流程仍沿单一路径继续 | JSON 格式优化、字段提取、文本处理、AI 分析 |
| `control` | 流程 | 改变执行路径、时序或作用域 | 条件分支、规则分流、延时、子工作流 |
| `integration` | 连接 | 与外部系统或服务交换数据 | HTTP 请求、批量 HTTP、应用动作 |
| `output` | 输出 | 面向人或外部目标呈现、保存或交付结果 | JSON 展示、记录结果、导出文件、发送消息 |

判断顺序：先看节点是否改变流程；再看是否调用外部系统；最后看它是产生、处理还是交付数据。AI 不是主分类，AI 决策属于「流程」，AI 生成属于「处理」。

### 2. 载体：能力由什么执行

沿用 `carrier` 作为筛选维度：`basic`、`data`、`ai`、`app`、`code`、`subflow`、`trigger`。载体用于筛选、颜色和权限提示，不再作为分组标题。

### 3. 标签：用户会用什么词搜索

标签承载主题和格式，例如 `json`、`文本`、`网络`、`时间`、`列表`。标签可以多选，只参与搜索和推荐，不产生新的一级分类。

## 目录准入

每个新节点进入公开目录前应具备：

1. 唯一且稳定的 `id`，以及清晰的动宾式名称。
2. 一句描述、主分类、载体和搜索标签。
3. 可推导的默认配置、明确的输入输出端口和可恢复的错误提示。
4. 至少一个执行测试和一个从面板插入后的产品测试。
5. 明确的成熟度：`experimental`、`beta` 或 `stable`；公开目录默认只展示 `stable`。

## 面板信息架构

- 默认态：显示「最近使用」和五个可折叠主分类，不平铺全部节点。
- 搜索态：跨名称、描述、标签、载体搜索，并在结果中显示主分类与载体。
- 筛选：载体作为可选筛选项；成熟度不暴露给普通用户。
- 键盘：上下键移动、Enter 插入、Escape 关闭，焦点与选中态必须可见。

## 下一步

1. 将 `category: string` 收紧为稳定的分类 ID，并添加 `tags`、`maturity`、`catalogVisibility` 元数据。
2. 按上述边界逐个审核历史节点；通过一个，公开一个。
3. 分类达到三个以上时，再把添加面板升级为分组/折叠视图。
